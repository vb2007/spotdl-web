# v72.1 — Worker Boot Memory (a booting worker fits its limit without swap)

Branch: `dev-worker-boot-memory` → PR into `main`
Version: `6.72.1`
Wave / slot: out-of-wave patch / 5
Depends on: v72 merged (it is; `6.72.0` never reached production, see below)

## Scope

Inserted by the owner on 2026-11-26, after v72 merged and before v73. It is a production
incident fix, so it ships before anything else deploys: **every deploy recreates `worker-meta`,
and until this lands every recreate fails the same way.**

**The incident (2026-11-26, read-only evidence from the host and the pipeline).**
- The `6.72.0` deploy (Release & Deploy run `45782916262`) failed its health wait at 08:41 UTC.
  `worker-meta` was in an OOM-restart loop. Docker's events showed `oom` then `die 137` about every
  20 s, and it reached 183 restarts.
- The rollback to `6.71.0` looped the same way. Nothing in v72 caused it.
- Beat's 30 s `dispatch_due_tracks` runs on `worker-meta`, so **no download was dispatched from
  08:34 to 09:50**. The alert watchdog was down with it.
- At the owner's direction, it was stopped over SSH with `docker update --memory 2g
  --memory-swap 2g spotdl-web-worker-meta-1`. That holds only until the container is recreated.

**Why it fit before.**
- The successful boot under 2 GiB peaked at **827 MiB** (the cgroup's `memory.peak`). It idles at
  460–480 MiB.
- The prod limit is 768M. Compose gives each container a swap allowance equal to its limit
  (`MemorySwap` = 2× `Memory` on every overlay-limited service).
- **The host's swap is full (975/975 MiB)**, so that allowance is empty and the limit is a hard
  RAM cap.
- `6.71.0`'s boot on 2026-11-25 15:35 passed with nearly the same ledger: swap absorbed the peak
  then. **The defect is the peak, not the swap. It was always above the limit, and only swap hid
  it.**

**Where the peak comes from (measured locally on 2026-11-26).** The parts were measured; their
overlap in production is inferred. The kernel's OOM task dump wasn't read: `journalctl -k`
returned nothing without root. The reproduction below confirms or refutes the overlap. The ledger
had 23,049 rows,
production's count from `reconcile_disk`'s own log line. Each process was measured by
`ru_maxrss`.

| Part of a `worker-meta` boot | Peak |
|---|---|
| A process that has imported `app.tasks.celery_app` | 222 MiB |
| `reconcile_disk()` on top of that (7.6 s, ORM load of the whole ledger) | +83 MiB |
| One healthcheck probe, `celery -A app.tasks.celery_app inspect ping …` (imports the whole app) | **233 MiB** |
| The same probe broker-only: `CELERY_BROKER_URL=… celery inspect ping …` (no `-A`) | 47 MiB |

- Docker documents a **5 s default `start_interval`** during the 90 s `start_period`, and it is
  unset here (Docker 29.10). If so, a probe is almost always running inside the cgroup while the
  boot's reconcile runs. Nobody has observed that cadence yet; the reproduction records it.
- Steady 480 + probe 233 + reconcile 83 is about 800 MiB, which is over 768 and close to the
  827 MiB measured.
- The broker-only probe answers the same `pong` from a live worker (exit 0). It exits 69 for a
  name that isn't online, so it still proves the named worker's control loop is alive, which is
  why the probe exists (`docker-compose.yml` beside `worker-dl`'s healthcheck).
- `worker-dl` and `worker-expand` carry the same probe. Their limits have room today
  (857 MiB of 1.5G, 266 of 768M), but every probe pays the same 233 MiB.

**`beat`** runs at 222 of 256 MiB, also without usable swap. It has no healthcheck and no boot
work, but 34 MiB of headroom is the next loop waiting to happen.

## Tasks

1. **Broker-only worker healthchecks.** Change `worker-dl`, `worker-meta` and `worker-expand` in
   `docker-compose.yml` to
   `CELERY_BROKER_URL="$$REDIS_URL" celery inspect ping -d <name>@$$HOSTNAME -t 10 >/dev/null 2>&1`.
   - Keep each `-d` name, `-t 10`, the interval, the timeout, the retries and the `start_period`.
   - **The URL stays in the environment, never in argv.** It carries the Redis password, and an
     argument shows in `ps`/`docker top` on the host. A `VAR=value cmd` prefix in the probe's shell
     doesn't reach argv; `celery -b "$$REDIS_URL"` would.
   - Celery reads `CELERY_BROKER_URL` for an app-less CLI call (verified 2026-11-26, Celery 5.6).
   - Update the comment beside `worker-dl`'s probe, which the other two point to. It should say
     why the probe must not import the app.
2. **`reconcile_disk` reads only what it needs.** `services/dedup.py`'s `reconcile_disk` loads only
   `(spotify_track_id, file_path)`, streamed (`yield_per`), not whole ORM rows.
   - It deletes by primary key.
   - **Keep every guard as it is:**
     - the per-root sentinel and unmounted-root skips (v57);
     - the re-read of a row before it is deleted, which covers the v34.1 race with a concurrent
       library sweep's repoint;
     - the "row already gone" path;
     - the log lines, which are the evidence production gives.
   - A row whose path changed since the stream read it is re-read by primary key, exactly as
     `db.refresh(row)` does now.
   - This one guards ledger growth: the ledger only grows, and the ORM load grows with it.
   - **If the measurement in "Done when" shows no real drop, revert this task and say so in the
     PR.** Task 1 alone fixes the incident.
3. **`beat`'s limit to 384M** in `docker-compose.prod.yml`. Measure its steady RSS on the slot
   stack first. If it is far below production's 222 MiB, report that instead of guessing.
4. **A regression guard.** A test fails if any `celery` healthcheck in `docker-compose.yml` passes
   `-A`/`--app` (the app import) or `-b`/`--broker` (the URL in argv). Put it
   next to an existing compose-reading test if one exists; otherwise make it a small pytest that
   parses the YAML.
5. **Docs.**
   - `docs/GOTCHAS.md` gets a v72.1 section and index lines:
     - the swap-backed limits (a limit only holds when the host's swap is free);
     - the probe's in-cgroup cost and the 5 s `start_interval` default;
     - "a passing boot yesterday proves nothing when swap filled since";
     - a dated note on v21's `worker-meta` OOM entry pointing here (its 768M sizing assumed
       swap).
   - `docs/DEPLOYMENT.md`:
     - the worker limits are sized to fit **without swap**;
     - how to read a container's `memory.peak`;
     - the one-line `docker update` stopgap for an OOM loop on a rollback target that predates
       this fix.
6. **Version** `6.72.1` in both files, plus `uv lock`.

## Out of scope

- **The host's memory and swap.** That is the owner's: Tube Archivist's Elasticsearch heap,
  `qbittorrent`, Plex. The fix must not depend on swap coming back.
- **Raising the `worker-*` limits** or changing `--concurrency`. The measured peak after task 1
  is about 610 MiB under a 768M limit.
- Setting `start_interval`. A cheap probe makes the cadence harmless.
- The `redis` service's own healthcheck, which passes its password on the command line.
  Note it for the owner; don't change it here.

## Deploy notes

No env var, no migration. Compose changes are the healthchecks and `beat`'s limit; run
`docker compose config` and the CI drift check.

**This is the first deploy that makes v72 live** (`6.72.0` was rolled back). v72's deploy notes
apply:
- The owner checks that their `GET /user` on vb2007.hu says `"isSuperuser": true` before their first
  spotdl login on `6.72.1`.
- The host `.env` keeps its `ADMIN_EMAIL` line for a rollback to `6.71.0`.

**Rollback caveat.** The rollback target (`.last-good` = `6.71.0`) still has the heavy probe, and
swap is still full. So if `6.72.1`'s deploy fails for another reason, its rollback loops exactly as
on 2026-11-26. The PR says so, and gives the owner the stopgap:
`docker update --memory 2g --memory-swap 2g spotdl-web-worker-meta-1`.

The deploy itself recreates `worker-meta` from compose (768M), which drops today's hand-set 2g.
That is intended once this ships.
