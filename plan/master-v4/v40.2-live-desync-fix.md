# v40.2 — Live Desync Fix (a settled job's lanes and chips catch up at once)

Branch: `dev-live-desync-fix` → PR into `main`
Version: `4.40.2`

## Scope

Inserted by the owner on 2026-10-14, after v40.1 merged and before v41. It was found while
verifying v40.1 on production. The last three Scooter tracks (job `6f1640ce`) went `lookup_failed`
20s apart. The job row already read `done — partial`, but:

1. **The Waterfall kept three lanes** at their last percentage (25–40%) for up to a minute.
   `queue.ts` keeps a lane for v23's 60s grace window after a track leaves `downloading`, so a
   fast fail-then-redispatch cycle doesn't flicker. Only `completed`/`skipped_duplicate`/
   `cancelled` skipped that window. `lookup_failed` waited it out, although nothing automatic
   ever re-dispatches it, and a hand retry's own `downloading` event re-adds its lane anyway.
2. **The state chips said "active 1 · done — partial 0".** `refreshJobRow` swapped the refreshed
   row without moving its count between status chips. The chips stayed wrong until a hard reload.
   Its 404 removal path, and `applyJobEvent`'s, dropped a row without decrementing its chip either.

The backend and database were correct throughout (read-only prod check). Frontend only.

## Tasks

1. `LANE_ENDING_STATES` = `TRULY_TERMINAL_STATES` + `lookup_failed`. A track event in one of
   these states removes its lane at once. `waiting` keeps the grace window.
   `TRULY_TERMINAL_STATES` (which also discards later events for a track) is unchanged, so a
   hand retry still revives the lane.
2. `refreshJobRow` patches through `patchPageJob` (no insert). When a row's `statusKey` changes,
   one count moves from the old key to the new one. Comparing against the row as it is now keeps a
   second re-fetch of the same status from moving anything.
3. `dropPageJob(jobId)` removes a 404'd row and decrements its chip and `totalEstimate`. Used by
   both 404 paths.
4. Unit tests for each behavior, plus the grace window still applying to `waiting`.
5. Docs: a dated correction on GOTCHAS' v23 grace entry, a Live progress index line, and a v40.2
   section; this plan's Amendments entry.

## Out of scope

- A job off the loaded page can't have its chip moved locally (its old status is unknown); it
  catches up on the next reload. Re-reading the jobs counts from the server (as v35 (g) does for
  tracks) would cover that, but it's a different design.
- How a lane looks during a `waiting` grace window (still the amber bar at its last percentage).
  That belongs to the v42 dashboard redesign.

## Deploy notes

- Frontend only. No migration, no env var.

## Done when

Each bullet needs its own evidence from the real local stack (`spotdlwebtest`, a real browser,
login through the real upstream, a real track).

- [ ] A track that goes `lookup_failed` while `/` is open loses its lane within a second.
- [ ] In the same run, the state chips move the job from "active" to "done — partial" without a
      reload, and match what a hard reload shows.
- [ ] The same run against the pre-fix `queue.ts` reproduces the bug (a lingering lane, stale chips).
- [ ] A hand retry of a `lookup_failed` track brings its lane back for the new attempt, and it
      leaves again at the verdict.
- [ ] `vitest`, `svelte-check` and `lint` are green; the new tests fail against the pre-fix store.
